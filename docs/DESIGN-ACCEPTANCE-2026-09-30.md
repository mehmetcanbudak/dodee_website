## React edition: supplied design consistency

Reviewed `sites/dodee-next/app/page.tsx`, `app/globals.css`, shared components, and current full-page Chromium captures at `test-results/react-browser/completion/final/chromium/home-1440.png` / `home-390.png`. Also visually inspected `completion/final/home-image-final/chromium-1440-1x.png` / `chromium-390-1x.png`, which include the final responsive hero image selection. The React application revision is `db5cdfa`; its evidence commit is `a6c19df`. These are revisions of the independent React repository, not the root static release.

This separate private alternative uses Fraunces/DM Sans, a cream background, an inset rounded hero, side-by-side desktop games, and a dark parent-guide card over a mint section. It does not implement the available Figma static-site component system, and it should not be silently restyled to do so. The final 1440 × 3749 and 390 × 3894 captures show readable hero copy clear of artwork, intact image proportions, a consistent rounded-card treatment, an explicit Watch action, a parent-guide action and single-column mobile content. They also show “No signup needed” wording and a YouTube-only follow link, with no signup form or email collection. These current images supersede the earlier signup-preview screenshots.

The final Chromium functional report records 53 passed checks with no uncaught errors, console errors or failed requests. The separate final image report records eight passed Chromium/WebKit cases covering 320px, 390px and 1440px widths and a 390px 2× display. It explicitly scopes its last follow-up to responsive image candidates and sizes, with geometry and behavior unchanged. On mobile, the tall hero still means substantial scrolling before the next section; whether that supports the intended watch journey is a usability question, not an established defect. These are local implementation observations, not a Figma overlay, accessibility certification, or owner approval. React publication would need its own release and acceptance decision.

## How to close this acceptance item

1. The static edition and production origin are selected, and corrected current desktop/mobile implementation captures have been reviewed. Record the verified release revision and final content state from the release ledger alongside this evidence.
2. Supply a current approved desktop Home node/export and, if exact mobile parity is required, a mobile composition. Confirm whether the surviving Design System components are normative for that edition.
3. Capture the chosen edition at the reference's exact viewport width and height, with loaded fonts, images, intended motion state and content; retain the screenshot, viewport, browser, URL and revision together.
4. Compare hero geometry, wave shape/height, card widths and padding, ornament layers/positions, navigation states, and mobile adaptations. Separate intentional accessibility/content changes from unintended differences; get approval for the former and fix the latter.
5. Record the reviewer, date, accepted edition/revision, and any accepted deviations. Leave this item open until that evidence exists.

Representative parent/caregiver validation is prepared separately in [USABILITY-ACCEPTANCE.md](USABILITY-ACCEPTANCE.md). No real-user sessions have been run for this review.
